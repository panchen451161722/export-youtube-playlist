实用的产品往往始于一项重复劳动。这个项目要解决的问题并不复杂：把一个公开的 YouTube 播放列表转换成结构化数据，让人们可以搜索、排序、归档或分析。

手动复制视频标题和链接很慢。已有工具通常只能处理少量视频，要求用户登录 YouTube，或者导出的文件包含的信息太少。简单脚本可以解决开发者自己的问题，却帮不到只想粘贴 URL 并下载文件的普通用户。

这个空缺成为了 [Export YouTube Playlist](/) 的起点。

## 我想解决的问题

播放列表在 YouTube 上看起来井然有序，但其中的信息很难在其他地方重复利用。研究人员可能需要标题和发布日期，课程创作者可能需要时长和频道名称，音乐整理者则可能希望在表格中获得链接、简介和公开互动数据。

第一版产品的目标被刻意控制在很小的范围内：

- 接受公开的 YouTube 播放列表 URL。
- 保留可用视频的原始顺序。
- 获取有用的公开元数据。
- 生成可用常见软件打开的文件。
- 不要求访问用户的 YouTube 账号。

保持第一版足够专注，也让后续技术决策清晰了许多。

## 从脚本变成网页流程

命令行脚本很适合验证原型。它可以解析播放列表 ID，请求播放列表项目，批量加载每个可用视频的详情，再把结果写入 CSV 文件。

但当其他人尝试使用脚本时，阻力就出现了：他们需要运行环境、依赖包、API 密钥、终端操作能力，还要有足够的信心排查错误。即使对脚本作者来说，每次重复这些设置也很麻烦。

网页版本把整个流程缩减为三个动作：

1. 粘贴播放列表 URL。
2. 选择一种或多种导出格式。
3. 下载生成的文件。

界面看似简单，但要让它稳定可靠，仍然需要认真处理输入验证、API 限额、文件生成和错误反馈。

## 使用官方 YouTube Data API

应用使用官方 YouTube Data API，而不是抓取 YouTube 页面。服务器从有效的 YouTube URL 中提取 `list` 参数，检查主机名和播放列表 ID，然后只请求导出所需的公开数据。

播放列表数据采用分页返回，因此服务需要持续请求后续页面，同时保留每个项目的原始位置。之后再批量获取视频详情，包括：

- 标题、简介、视频 URL 和缩略图。
- 频道名称和上传时间。
- 多种实用表示方式的视频时长。
- YouTube 提供时的公开观看、点赞和评论数。
- 简介中的标签、话题标签、链接和电子邮件地址。

已删除、私密、受限制或无法访问的视频可能没有完整信息。导出工具会跳过不可用项目，并在结果不完整或达到免费版 500 个视频上限时明确说明。

## 为失败情况而设计

成功流程很容易演示，真正困难的是在播放列表无法加载时准确解释发生了什么。

应用会区分多种常见情况：

- URL 中没有有效的播放列表 ID。
- 播放列表为私密、已删除或不可用状态。
- YouTube API 配额已耗尽。
- 上游请求耗时过长。
- 网络或 API 错误中断了请求。

请求设置了超时，播放列表响应不会被缓存，短时间限流也能减少意外的重复提交。界面会把服务错误转换成具体的处理建议，而不是只显示一条笼统的失败信息。

这些细节没有导出按钮显眼，却决定了一款小工具是否值得信赖。

## 在浏览器中生成文件

服务器返回结构化的公开元数据，浏览器负责生成可下载文件。这样既能让导出过程保持快速，也意味着生成的表格不会再次上传到应用服务器。

最初最实用的格式是 CSV 和 Excel，但不同工作流需要不同输出。现在导出工具支持 13 种格式：

- 用于电子表格的 CSV 和 Excel。
- 用于结构化数据的 JSON、XML、YAML 和 SQLite。
- 用于阅读和分享的文本、Markdown、HTML 和 Word。
- 用于在浏览器中保存链接的书签 HTML。
- 用于兼容播放列表应用的 M3U 和 M3U8。

选择一种格式时会直接下载对应文件；选择多种格式，或者不勾选任何格式，则会生成一个包含所需文件的 ZIP 压缩包。

所有格式都使用同一套经过规范化的字段。这种共享数据模型可以避免 CSV、表格、文档和数据库版本悄悄出现内容差异。

## 让简单界面值得信任

导出工具不需要复杂的控制台。它真正需要的是清晰的输入框、容易理解的格式选项、明确的进度状态和有效的反馈。

多项界面设计都来自这一原则：

- 在发起请求之前验证 URL。
- 说明支持公开和可访问的非公开播放列表。
- 在用户导出之前显示免费版播放列表限制。
- 预览已经加载的播放列表和视频数量。
- 确保操作在较窄的手机屏幕上仍然可用。
- 提供明确的成功和错误提示。

页面还解释了数据来源以及哪些信息不会被保存。处理链接和创建下载文件的工具，应该让用户很容易理解它的隐私模式。

## 隐私是架构的一部分

应用处理公开播放列表时不需要用户登录 YouTube，也不会请求订阅列表、观看记录或私密账号数据。

服务器只接收播放列表 URL，用它请求最新的公开元数据。导出文件在浏览器中生成，应用不会保存播放列表结果的历史记录。

这既是产品选择，也简化了技术架构。收集更少的用户数据可以降低风险，减少不必要的授权步骤，并让用户更快开始使用工具。

## 从主导出工具扩展到更多功能

主导出流程稳定以后，同一套公开数据还可以支持更小、更专注的工具。有些用户只需要一份干净的链接列表，另一些用户则需要标题、总观看时长、频道分布、标签、缩略图或频道信息。

这促成了一系列遵循相同原则的工具：

- 每个页面只解决一项明确任务。
- 处理公开数据时不要求登录 YouTube。
- 结果可以复制或下载。
- 统一处理不可用项目和 API 限额。

完整的播放列表导出器仍然是产品中心，而这些专用工具能为简单任务移除不必要的选项。

## 构建过程中学到的经验

最大的体会是：文件导出的核心并不是文件格式，而是数据质量和工作流程。

用户需要可预测的列、稳定的顺序、对缺失值的诚实处理、安全的表格输出，以及能够说明下一步该怎么做的错误信息。只有底层数据保持一致，支持多种格式才真正有意义。

我也学会让产品始终靠近最初的用途。过早添加账号、项目历史和复杂控制台很有诱惑力，但对这类工具来说，最快产生价值的仍然是最短的路径：粘贴公开播放列表，选择格式，然后下载有用的数据。
