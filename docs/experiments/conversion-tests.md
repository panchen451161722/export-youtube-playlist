# Conversion experiments

## CONV-2026-10-30-AUTH — Authenticate before backup checkout

- **Status:** not run; planned locally on 2026-10-30. The requested flow is implemented locally without a production split test or winner claim.
- **Hypothesis / audience:** requiring anonymous visitors who submit backup setup to sign in or register before checkout will improve account-linked checkout completion and reduce account-claim friction.
- **Control A / variant B:** A opens guest checkout and claims the account afterward; B saves the selected playlist, plan and preferences, opens authentication, then automatically opens authenticated checkout once eligibility is confirmed. Existing subscribers retain their current access and cannot purchase a duplicate subscription. Prices and trial rules are unchanged.
- **Primary metric / denominator / window:** distinct eligible visitors with a provider-confirmed positive payment within 14 days of their first setup submission / all distinct eligible visitors who submitted setup and have a complete 14-day window. Report registration, completed checkout and trial activation separately; free trials and zero-amount payments are not revenue.
- **Guardrails:** authentication failures, checkout errors, lost drafts, duplicate checkout attempts/subscriptions, cancellation loops, refunds and support complaints. Stop immediately for unintended charges, lost account ownership or duplicate subscriptions; investigate an error-rate increase above 1 percentage point versus control.
- **Proposed allocation / stopping:** 50/50 stable server assignment per first-party visitor, carried through account creation and checkout. Before launch, use baseline conversion to size for 80% power, 5% significance and a 20% relative minimum detectable effect. Enroll for 14–28 days, mature all 14-day outcomes, and report insufficient samples as inconclusive. No assignment or production traffic is enabled by this change.
- **Privacy / feasibility:** playlist drafts stay in sessionStorage; playlist URLs, account IDs and payment IDs are not added to authentication URLs or Clarity. Future experiment/variant exposure and outcome joins must remain first-party. A real split test is not feasible in this local task because stable assignment/exposure joins are absent and deployment is not requested. Validate the requested flow using regression tests, a browser fixture, TypeScript and a production build instead.
- **Planned / actual start and end:** launch not scheduled; actual start/end not run. **Deployment / commit:** not deployed; implementation is recorded in Git history for this file.
- **Samples / conversions / rates:** A: 0 / unmeasured / unmeasured; B: 0 / unmeasured / unmeasured.
- **Decision:** implement the requested flow; no experimental keep/revert winner decision.
- **Validation (2026-10-30):** all 30 draft, callback, checkout-path, pricing-action and locale-navigation regression tests passed; TypeScript, `pnpm build` and `git diff --check` passed. Browser checks against the production build with local fixture APIs verified Chinese setup → sign-in → sign-up → exactly one authenticated Pro checkout request, and German setup → sign-in → exactly one authenticated Pro checkout request. Playlist URL, Pro selection and weekly schedule were restored. Canceled checkout (including refresh), an existing subscriber, and ordinary/forged auth returns did not create checkout requests; a simulated checkout error displayed a recoverable message and did not retry on refresh. The fixture returned an example HTTPS destination; no live Stripe checkout, OAuth provider flow, email delivery, account creation, payment or deployment was performed. Browser-storage failure safely allows authentication but cannot restore a draft or auto-checkout; cross-device/new-tab draft restoration is not provided. Status remains **not run**, with no conversion outcome measured.

## RET-2026-10-28 — Private playlist reminder before cancellation

- **Status:** not run. Planned on 2026-10-28; local implementation only. No live split test or conversion improvement is claimed.
- **Hypothesis:** reminding subscribers that they can export video links and metadata from authorized private YouTube playlists will increase retained subscriptions without making cancellation harder.
- **Audience:** signed-in users with an active or trialing subscription who open the cancellation dialog in `/settings/billing`; analyze paid and trial cohorts separately. Exclude test accounts and repeat exposures from the denominator.
- **Control (A):** a plain cancellation confirmation, immediate loss-of-access notice, and keep/cancel buttons.
- **Variant (B):** the same confirmation with a private-playlist export reminder and a primary “Keep subscription” button. This is one retention-dialog treatment; do not attribute any result to its individual elements.
- **Shared rule:** both arms must accurately state that successful cancellation immediately stops renewal and paid features. The user requested this rule on 2026-10-28 before any experiment launched. This is a shared product rule, not an experimental difference. Confirming cancellation still takes one click in the dialog.
- **Primary metric:** seven-day retained-renewal rate: distinct exposed subscriptions with renewal still enabled seven days after first exposure / all distinct eligible exposed subscriptions with a completed seven-day window. Clicking “Keep subscription” alone is not retention or revenue.
- **Secondary outcomes:** separately report registration, completed checkout, trial activation, and provider-confirmed positive payments if applicable. Trial activation and zero-amount payments are never revenue. Trial-to-paid conversion is secondary and requires a positive payment.
- **Guardrails:** cancellation API failure rate, cancellation completion time after confirmation, cancellation-related support complaints, and refunds. Stop immediately for incorrect access/billing claims or blocked cancellation; pause for investigation if cancellation failures increase by more than 1 percentage point versus control.
- **Proposed allocation:** 50% A / 50% B, assigned once per account and experiment ID on the server and retained across devices. This allocation is not implemented or enabled.
- **Stopping criteria:** before launch, use the measured baseline to set a fixed sample size for 80% power, a two-sided 5% significance level, and a 5-percentage-point absolute minimum detectable effect. Run for at least 14 days, then wait for all seven-day windows. Stop enrollment after 28 days if the target sample is not reached and mark the result inconclusive; do not declare a winner from repeated interim checks.
- **Privacy:** store exposure, experiment ID, variant, and relevant subscription outcomes only in first-party reporting. Do not send account, subscription, or payment identifiers or authenticated cancellation events to Clarity.
- **Why no live split test:** the current first-party funnel summarizes checkout flows but has no cancellation exposure records or stable experiment assignment. This local change does not add that storage/reporting infrastructure or launch production traffic. A live experiment needs those prerequisites and an authorized deployment.
- **Alternative validation:** review the copy against private-playlist export support and provider cancellation behavior, run existing billing/cancellation regressions, and run `pnpm build`. Record results below after validation.
- **Planned start/end:** not scheduled; proposed enrollment duration 14–28 days plus outcome maturation. **Actual start/end:** not started / not ended.
- **Deployment / commit:** not deployed; implementation in the billing UI/translations, Stripe cancellation, and payment service is recorded in Git history for this file, with regression coverage. Stripe uses its [immediate cancellation API](https://docs.stripe.com/api/subscriptions/cancel) with `invoice_now: false` and `prorate: false`; no automatic refund is introduced.
- **Samples / conversions / rates:** A: 0 / not measured / not measured. B: 0 / not measured / not measured.
- **Decision:** no keep/revert winner decision; validate the requested local treatment, then evaluate a future instrumented split test. No effectiveness evidence yet.
- **Validation results (2026-10-28):** `pnpm build` passed. All 48 relevant tests passed across Stripe, legacy-account routing, payment service, subscription access, collection quota, and billing rendering (the two files with initially failing test fixtures passed on rerun). Coverage includes immediate active/trial cancellation, rejection of scheduled-only cancellation responses, owner checks, idempotent retries, webhook reconciliation, and removal of paid export/collection access while preserving access on failure. Browser checks using the actual billing page and local fixture APIs confirmed that “Keep subscription” dismisses the dialog and “Cancel now” produces the no-active-subscription state and a canceled history row. A screenshot of the Chinese dialog was saved for review. `git diff --check` passed. No production payment or live cancellation was performed; no retention outcome was measured.
